# Pegasus grammar conformance corpus

Corpus version **0.1.6**, written against grammar **v0.1.2 (draft)**.

This directory holds the hand-written `.peg` source cases and the lexer-stage candidate goldens. The `.tokens` and `.filtered` files were generated by the hand-written Rust lexer and are explicitly marked as unreviewed candidates; they must be checked against the grammar and frozen group by group. Parser-stage syntax-tree goldens (`.tree`) do not exist yet; the parser is checked through first-error positions and the hand-written `shape` and `stmts` oracles (see [Golden files](#golden-files)).

Status: every case has been run through the hand-written lexer, newline filter (`compiler/lexer`) and parser (`compiler/parser`), and all checks pass (see [Conformance checks](#conformance-checks)). Each accepted case parses without errors, each `P` case reports exactly its first error, and every `shape` and `stmts` header matches the parser's tree. `tools/corpus.py` checks the corpus format, error offsets and coverage, not the grammar itself.

## Layout

```
tests/grammar/
  README.md            this file
  diagnostics.toml     stable message IDs (L = lexical, P = parser/filter)
  coverage.toml        grammar production and rule -> case matrix
  cases/
    phase0/            every code example from the Phase 0 spec       P0-NNN
    lexical/           tokens, literals, comments, encodings          L-NNN
    newline/           newline-filter rules and header state          N-NNN
    precedence/        every precedence level and associativity       E-NNN
    ambiguity/         grammar section 7 rules A-I                    A-NNN
    items/             items, types, patterns, statements             I-NNN
    recovery/          first-error position and recovery behaviour    R-NNN
    parser/            parser-stage rules: 2a, rule B, nesting limit  S-NNN
  goldens/
    REVIEW.toml        per-group review state and hashes of source + golden files
    MANIFEST.toml      future provenance for independent parser/tree goldens
    candidates/        unreviewed .tokens and .filtered snapshots (360 files)
```

## Case format

Every case starts with header lines beginning `//@ ` (an ordinary line comment to the lexer), then a blank line, then the program.

```
//@ id: E-004
//@ tags: precedence, expr.power, expr.unary
//@ expect: accept
//@ shape: (neg (** 2 2))

fn t() = -2**2
```

| Key | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Stable ID, `<prefix>-NNN`; the file name starts with it. IDs are never reused. |
| `tags` | yes | Comma-separated feature tags (`family.detail`), used for coverage reports. |
| `expect` | yes | `accept` or `reject`. |
| `error` | reject only | `CODE offset=N near="text"`: message ID, UTF-8 byte offset, and the source text at that offset. |
| `shape` | optional | Expected tree of the body of `fn t` (or of the file's only function, if there is no `fn t`), in the notation below. An independent oracle for precedence and ambiguity cases. |
| `stmts` | optional | Number of statements in the body of `fn t` (or of the file's only function). Checks newline and separator handling. |
| `value` | optional | `NAME = "text"`: the value of the string literal in `const NAME`, with escapes. Used for raw-string line-ending normalization. |
| `warning` | optional, repeatable | `CODE offset=N near="text"` for each expected warning (W codes). Accepted cases may carry warnings. |
| `nl-kept`, `nl-dropped` | optional, repeatable | `offset=N near="\n..."`: this NEWLINE (at byte N) must survive / be dropped by the newline filter. Hand-written filter assertions, checked independently of any golden. |
| `note` | optional | Free text for reviewers. |

### Error positions

- `offset` is the **UTF-8 byte offset**, counted from 0 at the first byte of the file (including the header and any BOM), of the first byte of the token where the **first** error is reported. This is the normative value.
- Line and column are derived, never stored: lines are 1-based and split at LF (a CR LF counts as one line end); columns are 1-based and count Unicode scalar values from the start of the line.
- `near` is the exact source text at that offset. It exists so a reviewer can see what the offset points at, and so the tool can recompute offsets after edits. Escapes allowed inside `near`: `\r \n \t \\ \" \xHH \u{XXXX}`. If the text occurs more than once after the header, append `#N` to pick the Nth occurrence.
- Only the first error is normative. Later diagnostics are checked only for the recovery properties in grammar section 8.

### Shape notation

Shapes are S-expressions describing the syntax tree of a single expression, ignoring parentheses and spans.

| Form | Meaning |
| --- | --- |
| `a`, `42`, `i32` | Name, literal or type |
| `(op lhs rhs)` | Binary operator, written as in source: `+ - * / % ** << >> & ^ \| == < && \|\| +% *% +\| ...` |
| `(neg x)` `(pos x)` `(not x)` `(bnot x)` | Prefix `-`, `+`, `!`, `~` |
| `(await x)` `(try x)` | `await x`, `x?` |
| `(call f args...)` | Call of a callee that is not a field access |
| `(mcall recv name args...)` | Call whose callee is `recv.name` |
| `(gcall f (T...) args...)` | Generic call `f<T...>(args)` |
| `(gmcall recv name (T...) args...)` | Generic method call `recv.name<T...>(args)` |
| `(gpath Name (T...))` | Path step with generic arguments, e.g. `Vec<i32>` in `Vec<i32>.new()` |
| `(field x name)` | Field or tuple access `x.name`, `x.0` |
| `(index x i)` | `x[i]` |
| `(cast x T)` | `x as T` |
| `(range a b)` | `a..b` (`range=` for `..=`) |
| `(closure (params...) body)` | Closure |
| `(struct Path (field value)...)` | Struct literal |
| `(tuple a b ...)`, `(repeat v n)` | Tuple, array repeat `[v; n]` |

## Tooling

```
python3 tools/corpus.py check         # validate format, IDs, codes and offsets
python3 tools/corpus.py coverage      # production/rule -> case matrix; lists gaps against targets
python3 tools/corpus.py fix-offsets   # recompute offset= from near= after editing a case
python3 tools/corpus.py stats         # counts by directory, outcome and tag family
python3 tools/test_goldens.py        # adversarial tests for the review/freeze manager
```

`.github/workflows/corpus.yml` runs `check` and `coverage` on every push and pull request, and verifies the byte-sensitive fixtures (CR LF, lone CR in source, raw strings and block comments, LF-only L-029, BOM, invalid UTF-8) arrived unaltered.

## Coverage and targets

`coverage.toml` maps every production of `spec/pegasus.ebnf` (all 157, lexical and syntactic) to the cases that exercise it. Three further sections are not productions: `[filter]` for the newline-filter rules (prose in grammar section 3), `[categories]` for encodings, constraints and recovery behaviour, and `[rules]` for ambiguity rules A–I.

`coverage` reads the production list from `spec/pegasus.ebnf` itself and fails if a production is missing from the matrix, if a matrix entry is not a production, if a listed case does not exist, if any entry has no case, or if any case is mapped nowhere. It reports, without failing, entries below their target (3 per lexical token and filter rule, 2 per production and category, 10 per ambiguity rule).

The lexer-stage harness decodes the `value` headers (L-029/L-030) and asserts that LF and CRLF raw strings have the same value (`one\ntwo`). These are executable lexer checks, not merely metadata.

This corpus is a seed. The grammar's acceptance criteria require at least 1,000 accepted and 500 rejected programs, 10 cases per ambiguity rule, every precedence pair, fuzzing and incremental-parsing tests. Version 0.1.6 has 128 accepted and 52 rejected cases; `coverage` shows exactly where the gaps are. Passing `check` and `coverage` shows the corpus is well-formed, not that any parser conforms.

Edit cases with an editor that preserves bytes exactly. `.gitattributes` marks `cases/` as binary to git so CR LF and lone-CR cases are never rewritten on checkout.

## Conformance checks

`pgcorpus verify` (also run by `ctest`) checks, for every case:

1. **Rejected with an `L` code:** the lexer's first diagnostic has exactly that code at exactly that byte offset.
2. **Accepted, or rejected with a `P` code:** the lexer reports no errors.
3. **Warnings:** the lexer's warnings equal the case's `warning:` lines exactly, by code and offset; a case without `warning:` lines must produce no warnings. Warnings never make a case rejected.
4. **`value:`:** the decoded literal equals the stated value (L-029 and L-030 must both decode to `one\ntwo`).
5. **`P` errors at a line end** (`near` starts with `\n`): that `NEWLINE` survives the newline filter.
6. **`nl-kept` / `nl-dropped`:** the stated NEWLINE survives / is dropped by the filter.
7. **Candidate goldens:** if `goldens/candidates/<id>.tokens` or `.filtered` exists, current output must match it byte for byte.
8. **Accepted:** the parser reports no errors.
9. **Rejected with a `P` code:** the first error, with lexer and parser diagnostics merged by offset (lexer first on a tie), has exactly that code at exactly that byte offset.
10. **`shape:`:** the body of `fn t` renders to exactly that S-expression.
11. **`stmts:`:** the block body of `fn t` has exactly that many statements.

Check 5 and the `nl-` checks concern the filter alone, so a NEWLINE that rule 2a makes dormant counts as dropped there; whether it ends a line is decided by the parser (grammar section 3) and checked by checks 8–11.

### Candidate goldens and their review

`goldens/candidates/` holds token and filtered-token streams written by `pgcorpus bless` from the **hand-written lexer**. They are regression snapshots, marked `candidate-unreviewed` in their `PROVENANCE.toml`. A human review against the grammar can freeze them as lexer-stage regression goldens, but they are not an independent implementation oracle. A separately generated reference implementation remains a future cross-check. Re-run `bless` only deliberately, after reviewing the diff.

### Reviewing and freezing (gate 2)

Because the candidates come from the implementation under review, they can faithfully preserve a lexer bug; agreement with themselves proves nothing. Each group is therefore reviewed **against the grammar specification** and then frozen:

```
python3 tools/goldens.py status                                   # which groups are reviewed
python3 tools/goldens.py freeze lexical --reviewer "Name" [--scope "..."]
python3 tools/goldens.py check                                    # CTest and CI run this
python3 tools/goldens.py check --require-all-frozen                # Gate 2: the seven Phase 1 groups
python3 tools/goldens.py check --require-phase2-frozen              # parser-milestone gate: the parser group
python3 tools/goldens.py unfreeze lexical --reason "why"          # only to change a frozen group
```

State is in `goldens/REVIEW.toml`: each frozen group records its reviewer, date, scope, SHA-256 hashes of every `.peg` source case, and SHA-256 hashes of every `.tokens`/`.filtered` candidate. `check` fails if a source or golden changes, or if a frozen group gains, loses or renames cases. Manifest parsing validates the TOML structure and the consistency of the recorded snapshot; live inventory drift is reported by `check` and `pgcorpus bless`, rather than making the manifest unloadable. This distinction is deliberate: even after a legitimate source addition, removal or rename, `unfreeze GROUP --reason "..."` must remain available to release the group for re-review. Missing or malformed manifests, unsafe paths, invalid hashes, incomplete entries and inconsistent review history still fail closed. `pgcorpus bless` asks this validator for the protected-file inventory before writing anything; it refuses to run if the manifest, current inventory or any frozen source/golden hash is invalid, never overwrites a frozen golden, and exits with failure if lexer output differs from a frozen golden. `unfreeze` requires a reason, kept in the file's history, and the group then needs a new review. `check --require-all-frozen` fails until the seven Phase 1 groups are frozen; use this as the final Gate 2 check. The `parser` group (Phase 2) has its own gate, `check --require-phase2-frozen`, so adding parser cases never changes what Gate 2 requires. The tool records a review; it cannot verify that one took place, so the reviewer field is the accountability.

Groups are the case directories: `phase0`, `lexical`, `newline`, `precedence`, `ambiguity`, `items`, `recovery`, `parser` (180 source cases and 360 candidate golden files in this corpus version; the first seven groups are byte-identical to R6.2). Reviewed and frozen candidates serve as the manually inspected lexer-stage regression goldens. They are not an independent implementation oracle: the reviewer checks them against `spec/grammar.md` and `spec/pegasus.ebnf`. When a generated reference implementation exists, its output will also be compared against the frozen files, and every disagreement investigated against the grammar.

## Golden files

Goldens are generated, not hand-written, but they are not trusted just because the lexer produced them. The lexer-stage candidates are reviewed against the written grammar and frozen with their source inputs. Future parser-stage goldens will additionally use an independent reference implementation.

1. **Grammar-based review.** The current `.tokens` and `.filtered` candidates come from the handwritten Rust lexer. Before freezing, a reviewer inspects them against the grammar, with particular attention to ambiguity, precedence, newline and recovery cases. Their source inputs are frozen alongside them, so a later source edit invalidates the review.
2. **Unambiguous positions.** Token spans and diagnostic offsets use UTF-8 byte offsets, using the same convention as `error offset=`.
3. **Provenance and controlled change.** `goldens/REVIEW.toml` records per-group reviewer metadata and hashes for every source and candidate golden. `goldens/MANIFEST.toml` is reserved for future independent-reference and parser/tree golden provenance. Goldens are never regenerated during ordinary test runs. A test that disagrees with a frozen golden **fails**; changing a frozen group requires an explicit `unfreeze` with a reason, a deliberate `bless`, and a new review.

Current lexer-stage files per case:

```
goldens/candidates/<id>.tokens      lexer output, before the newline filter
goldens/candidates/<id>.filtered    token stream after the newline filter
```

Parser-stage files to be added later:

```
goldens/<id>.tree                  syntax tree (accepted cases) or error list (rejected cases)
```

## Adding a case

1. Pick the next free ID in the directory; never reuse a retired one.
2. Write the header and program. For a rejected case, write `error: CODE near="..."` without an offset.
3. Run `tools/corpus.py fix-offsets`, then `check`.
4. If the case tests behaviour the grammar does not state, fix the grammar first. The corpus never encodes undocumented exceptions.
